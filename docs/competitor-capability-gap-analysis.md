### 1.3 Parloq 核验口径

- “已实现”必须能在当前仓库的路由、模型、页面和/或执行链路中找到，不只看 README 或菜单名称。
- “拉群营销”当前只有建设中页面，明确不计为业务能力。
- 协议同步虽然可以配置联系人、聊天、消息历史等信号，但当前数据面只把计数和摘要放入账号 metadata；系统明确不保存入站正文、回复正文、完整聊天记录或入站媒体。因此本文不会写成“已实现完整聊天同步/客服收件箱”。

### 2.1 先看结论

1. **需要优先补的是控制面安全与可追责性，不是再加一个菜单。** Parloq 已有登录失败锁定、Turnstile、可选 TOTP、恢复码、管理员重置、会话撤销和细粒度动作权限；仍缺统一操作审计账本、敏感操作再认证和敏感导出审计。
2. **同行的核心竞争力来自双端分工后的完整闭环。** 买量端负责模板、域名、渠道、Pixel/CAPI 和配对漏斗，云控端承接账号资源、协议和营销任务；两个入口属于同一系统，具体账号与指标链路仍需验证。`【U】【D】【V】`
3. **公开文档不能再作为同行能力上限。** 买量端统计页当前已有导出入口、回传成功/失败、访问时长、账号质量和裂变指标；两个端的菜单管理又揭示了公开手册及演示侧栏未覆盖的产品域。本文以 `【M】` 确认当前产品范围，以 `【E】` 确认当前页面，以 `【D】` 保留规则口径，不擅自推定菜单背后的执行完成度。
4. **买量获客端的核心链路 Parloq 基本覆盖并已有超出项。** Parloq 已有自包含模板 ZIP、私库导入、模板版本与质量、渠道、域名、Meta Browser Pixel+CAPI、漏斗、裂变、账号质量和 CSV；无需按买量端的独立信息架构再拆一套后台。
5. **Parloq 的一体化仍是架构优势。** 同行两个入口的技术数据链路仍需验证；Parloq 的准确优势是同一代码库与资源模型可直接串联渠道、账号、协议、代理、任务和统计。
6. **生产可靠性仍缺最后一块。** Compose 健康检查、Alembic、带 Git SHA 镜像、发布锁、配置备份和失败回滚都已具备；定时加密数据库备份、恢复演练和明确 RPO/RTO 尚未落地。

## 4. 可执行优先级清单

### 4.1 需要对齐

#### P0：生产安全与数据可靠性

1. **把已完成的 TOTP 登录基线复用于敏感操作。** 当前已有可选绑定、登录挑战、恢复码、管理员重置、防重放和 MFA 专项安全事件；下一步覆盖管理员改密/改权限、平台密钥修改、账号凭据导出、域名购买和批量删除，并为这些动作要求短时再认证。
2. **建立统一操作审计账本。** 最小字段：`actor_user_id`、会话/请求 ID、动作、资源类型与 ID、结果、失败原因、来源 IP 哈希、UA 摘要、before/after 的脱敏差异、发生时间。第一批覆盖登录/锁定、用户/角色、系统凭据、账号导出、删除、域名订单、Pixel/CAPI 配置、任务状态变更。
3. **落地加密数据库备份和恢复演练。** 明确 RPO/RTO、保留周期、异地副本、加密密钥边界、备份校验、按季度恢复演练；备份必须覆盖 Baileys creds 和完整 Signal Key Store，同时严格限制访问。
4. **补强账号导出保护。** 在现有“必须验证完成 + 必须离线 + 权限控制 + no-store”基础上增加 MFA、审计、短时一次性下载或服务端临时包清理；保持“导出不自动注销/删除”的安全语义，不照搬云控端的不可逆迁出。

#### P1：近期竞争力

5. **把异常变成可处理的告警。** 先覆盖节点不可用/容量满、代理异常、账号失效率突增、Worker 心跳、磁盘阈值、CAPI 连续失败和 Meta 域名异常；至少提供规则、持续时间、当前/恢复状态、责任人和一种通知通道。
6. **完善账号质量与风险解释。** 不再把“头像 + 群组”两项分数称为广义账号质量；增加字段可用性、来源质量、连接稳定性、发送后失效、代理/节点关联等分项，并允许显示“未知”。
7. **增加超链预发布/周期模式。** 复用现有动态分组、策略快照和 Worker 唤醒机制，明确结束条件、每轮目标去重、期间新账号加入、暂停恢复和版本语义；不要先复制云控端的全部表单再补执行模型。
8. **加强市场透视的可行动性。** 核对发信国×收信国、小时粒度、成功/送达/账号损耗和号均口径；从异常单元格能回到任务、账号、协议或代理筛选。
9. **统一登录后落点。** 登录成功进入真实工作台 `/`，再按权限处理空模块；避免每个用户固定进入模板管理。

#### P2：操作效率

10. 为高频表格增加保存视图/列偏好，优先账号池、任务明细、渠道统计和市场透视。
11. 为复杂策略提供“最终有效吞吐”和风险摘要，避免运营自行相乘 QPS、并发账号、Worker 和网关上限。
12. 为 IP、数据包和账号导入提供可下载模板、前置预检、随机样本核验和失败结果下载；保留 Parloq 更宽松但可控的格式解析。
13. 扩充运营版内嵌手册：指标口径、状态枚举、常见错误、恢复路径和高风险操作自检清单。

### 4.2 可借鉴但不必照搬

- **按业务拆成两个后台：** 同行用买量端和云控端降低单端的信息密度，适合角色、发布节奏或安全边界明显不同的团队；代价是身份、资源主键、权限、状态流转和指标归因的跨端一致性。Parloq 应先用角色工作台、菜单权限和渐进式导航解决复杂度，除非组织和隔离需求足以证明物理拆分的收益。
- **云控端的不可逆账号迁出：** 它适合“导号”业务语义，不适合作为 Parloq 通用备份导出默认。Parloq 应把“备份导出”和“迁移并退出”拆成两个显式工作流。
- **买量端的人工 Facebook 数据录入：** Parloq 已支持同类日指标和 CSV。只有真实广告账户授权量足够时再接 Marketing API，不必为“自动化”提前承担多账户 OAuth 和数据延迟复杂度。
- **高频 DevTools 检测和跳空白页：** 只能增加分析成本，不能保护已下载的前端资源。Parloq 继续依赖服务端鉴权、CSP、签名、幂等、限速和敏感数据不下发。
- **同行两端的全部白话提示：** 应借鉴关键路径和高风险操作，不必给每一列都堆叠长 tooltip；优先让指标定义可点击追溯到统一口径。

### 4.3 Parloq 独有或明显优势

- 买量接入、账号资源、协议代理、发送任务和统计使用同一套代码与资源模型，这是结构性优势；同行两个入口的账号主键与事件链路仍待验证。
- 推广模板 v2 自包含规范、ZIP/私库目录双入口、版本替换、质量报告、多语言/RTL、设备预览和白标组件。
- 可复用脚本/iframe 集成包，带来源域、SRI、版本、模板绑定、独立事件账本和限速边界。
- 域名接入、DNS/TLS 验证、NameSilo 询价/订单、Cloudflare 和宝塔自动开通的完整生命周期。
- 协议节点容量、配对限速、按需/持续连接、协议池路由和同步策略快照。
- 固定代理贯穿配对、重连、Socket 和媒体请求；支持多种分配模式、健康排除、容量和 fail-closed。
- 兼容 creds 与完整 Signal Key Store 的会话导入/导出，以及导入后的真实连接验证。
- 超链任务的模板/策略/数据包版本快照、动态账号分组、sticky 槽位、失败换号、账号冷却和下发/发送两层状态。
- 菜单权限之外的动作权限，后端对未配置接口默认拒绝。
- Meta Dataset 资源化、Browser Pixel/CAPI 分离、事件映射、投递重试账本、trace、探测和域名受限信号。
- 系统内统一管理并测试 NameSilo、Cloudflare、宝塔和 GitHub 凭据。

2. 生产域名登录后的菜单与演示租户是否一致；“中央云控”与“极量乌云CRMS”是品牌更新、部署品牌还是子产品命名。
3. MFA 是否有恢复码、强制策略、可信设备和管理员操作审计。
4. 协议节点的真实技术边界、会话持久化位置、节点故障转移和配对限速。
5. 超链任务的自动重试分类、退避、账号补位、幂等和重复收信防护。
6. 是否有审计日志、主动告警、集中日志、备份、恢复、升级和回滚工具。
7. 导出 ZIP 的加密、一次性下载、保留时间、内容格式和迁出后会话清理是否与手册一致。

### 5.2 同行体系·买量获客端

1. 生产域名在普通用户浏览器中的当前登录页与登录后版本；本轮只在演示域名成功使用已有登录态，生产入口仍被页面保护阻断。
2. 生产域名 2026-07-06 构建与演示域名当前页面是否同版本、同发布分支或同租户能力集。
3. 菜单注册的“团长统计 / 账号分析”是否已实现、由什么角色或套餐开放；演示租户侧栏当前未显示。
4. 模板当前数量、实际登录方式、可配置参数、版本更新和发布流程。
5. 渠道的域名验证、证书、停用行为、FB/IG 内置浏览器行为和 Pixel/CAPI 投递账本。
6. 当前“导出”按钮的文件格式、字段、权限和成功条件；手工广告费用是否已有批量导入或 Marketing API 同步。
7. 普通用户的 `creator_id` 数据范围是否覆盖所有接口，official 代建资源如何转移。
8. 是否存在审计、告警、备份、升级和运维控制面。
9. MFA 引导是否可长期跳过、是否支持强制绑定、恢复码和管理员审计。
10. 页面保护是否会误伤普通用户、无障碍工具或企业安全软件；其行为不能反推为安全能力。

### 5.3 同行体系·跨端关系

1. 两端是否共用同一用户目录、登录会话、MFA 绑定和角色，还是仅在商业上属于同一系统。
2. 买量端配对成功后，账号是否自动进入云控端账号池；使用什么账号主键、去重规则、状态延迟和失败补偿。
3. 买量端渠道的归属用户、国家、模板和 Pixel 数据，是否与云控端的渠道、协议、账号来源和营销资格建立可追踪关联。
4. 两端是否共享租户边界与数据权限；official、上级用户、creator/owner 等概念如何映射。
5. 是否能从买量成本和配对漏斗一直追踪到账号寿命、营销任务、送达、封号和迁出，还是需要人工导出后关联。
6. 账号在云控端解绑、失效或迁出后，买量端是否收到回写并调整归因、渠道质量或继续投放策略。
7. 两端审计、告警、版本发布和灾备是统一平台能力还是各自维护。

### 5.4 演示站菜单注册项的完成度

云控端菜单管理当前列出了演示租户侧栏之外的超链全套、拉群/验群/拉粉、账号导入/转移/分组/养号、群组资产和交易市场。买量端还列出团长统计与账号分析。`【M】`

这些名称只能证明菜单注册存在。要升级为“已实现”，至少需要在获授权角色下验证：页面可打开、核心查询有数据、创建流程能通过校验、后台任务真实执行、状态/回执可追踪、失败路径可恢复，并核对与当前公开文档的版本关系。未完成这些验证前一律保持 `【V】`。

## 7. 后续维护方式

每次重新盘点时按下面顺序更新，避免把新文档覆盖成“新事实”：

1. 分别记录公开生产入口、公开文档和已登录演示站的访问日期与版本线索；不同构建时间只说明独立发布节奏，不再据此视为两个产品。
2. 先更新证据索引，再更新矩阵；每条同行结论保留 `【U】/【D】/【O】/【E】/【M】/【I】/【V】` 中适用的状态。
3. 有登录权限时分别记录“侧栏开放”“页面实际可打开”“只在菜单管理注册”三种状态，并验证买量端→云控端的账号、身份、权限和指标链路；只看到名称或按钮不等于后端成功。
4. Parloq 每次更新到新的 Git SHA，重新核对模型、路由、Worker、网关、前端页面和部署脚本；建设中页面继续单独标记。
5. 新增能力先判断是“需要对齐”“可借鉴”“Parloq 优势”还是“待验证”，再调整优先级，避免矩阵直接变成需求堆栈。
6. 涉及聊天记录、账号凭据、代理密钥、Pixel Token 和数据库备份的能力，必须同时更新隐私、安全、审计和恢复边界。
